1. EL MODELO C4 (diapositivas 5-8)
--------------------------------------
Qué es: estándar para elaborar diagramas de arquitectura de software
en distintos niveles de "zoom", útil para audiencias distintas
(desde stakeholders no técnicos hasta desarrolladores).

Nivel 1 — Diagrama de contexto del sistema:
  - Muestra el sistema que se construye (caja central) y cómo encaja
    en el mundo: qué personas lo usan y con qué otros sistemas de
    software interactúa.
  - Color azul/amarillo → el sistema que se está construyendo.
  - Color rojo → sistemas externos ya existentes (no se construyen
    en este proyecto, pero el sistema depende de ellos).

Qué tener en cuenta: el Nivel 1 NO muestra componentes internos ni
tecnologías — solo el límite del sistema y sus interacciones externas
(actores humanos + sistemas externos).

TechCup?") se resuelve como parte de TALLER_#6 — ver
Talleres/TALLER_6_explicacion.txt, sección del Diagrama C4.


2. ANÁLISIS DE REQUERIMIENTOS (diapositivas 10-24)
--------------------------------------------------------
Qué es un requerimiento: condición o capacidad que debe cumplir el
sistema para satisfacer una necesidad. Debe ser: bien escrito,
coherente, no ambiguo, medible y verificable.

Tipos:
  - Funcionales: qué debe HACER el sistema.
    Ej.: "Enlace académico debe permitir registrar la nota de cada
    tercio para cada estudiante de DOSW".
  - No funcionales: qué CUALIDAD debe tener el sistema (rendimiento,
    seguridad, usabilidad...).
    Ej.: "El sistema debe responder en máx. 2 segundos para el 95%
    de las peticiones con hasta 300 usuarios concurrentes".

Técnicas para recolectar requerimientos: entrevistas, encuestas/
cuestionarios, observación, workshops.

Proceso de análisis:
  1. Listar requerimientos de alto nivel.
  2. Detallar cada requerimiento.
  3. Agrupar por módulos y categoría (funcional/no funcional).
  4. Identificar relaciones, ambigüedades, contradicciones, preguntas.
  5. Consolidar en la matriz de trazabilidad.

Documento de análisis de requerimiento (plantilla, diapositivas 20-24):
  - Nombre e identificador único (ej. THCP-01).
  - Descripción y cómo se ejecuta.
  - Actor principal.
  - Precondiciones.
  - Datos de entrada/salida (lo que el actor entrega, lo que el
    sistema responde — "cruza la frontera del sistema").
  - Flujo básico (pasos) y flujo alterno/excepciones.
  - Mockup de pantallas + diagrama de caso de uso asociado.
  - Reglas de negocio (restricciones del dominio real, no del
    software) + glosario + control de versiones.

Qué tener en cuenta: las reglas de negocio son del DOMINIO (ej. reglas
de una universidad), no decisiones técnicas — no deben mezclarse con
detalles de implementación.


3. DIAGRAMA DE CASOS DE USO (diapositivas 26-30)
------------------------------------------------------
Qué es: diagrama UML de comportamiento para visualizar roles (actores)
y cómo interactúan con el sistema. Útil para presentar una vista de
alto nivel a administradores/stakeholders.

4 objetos: Actor, Caso de Uso, Sistema (límite, rectángulo — opcional
pero útil en sistemas grandes), Paquete (agrupa casos de uso,
opcional).

Cómo crear uno:
  1. Identificar los actores que interactúan con el sistema.
  2. Identificar los casos de uso (qué necesitan los actores del
     sistema).
  3. Buscar funcionalidad común reutilizable → extraerla como caso de
     uso separado, conectado con <<include>> (siempre se ejecuta) o
     <<extend>> (se activa opcionalmente, con una regla de extensión).

Reglas (diapositiva 30):
  - Regla 1: al menos un diagrama de caso de uso por requerimiento.
  - Regla 2: al menos un requerimiento por diagrama de caso de uso.

Qué tener en cuenta: <<extend>> no siempre implica "opcional" — el
caso de uso base debe poder ejecutarse por sí mismo aunque no se
llame el caso de uso que lo extiende.


4. PROTOTIPOS Y MOCKUPS (diapositivas 32-39)
--------------------------------------------------
Prototipo: representación preliminar del sistema, construida ANTES
del desarrollo real, para validar ideas con usuarios/stakeholders. No
funciona de verdad — simula cómo se verá y usará. Objetivo: comprobar
que se entendieron bien los requerimientos antes de programar.

Mockup: representación visual de una interfaz (sin funcionar de
verdad). Muestra: pantallas, layout de componentes, CTAs (llamados a
la acción), elementos (botones, textos), navegación entre pantallas.

Para qué sirven: visualizar la interfaz, validar requerimientos,
probar flujos de navegación, detectar problemas de usabilidad, alinear
usuarios/diseñadores/desarrolladores.

Flujo funcional (navegación): secuencia de pantallas y acciones que
sigue un usuario para completar una tarea. Incluye: pantallas,
acciones del usuario (clics, selecciones), decisiones (sí/no),
resultados (éxito/fallido).

Herramienta mencionada: Figma (diseño colaborativo, prototipos
realistas, sistemas de diseño).


5. HEURÍSTICA DE NIELSEN (diapositivas 40-51)
---------------------------------------------------
Qué es: 10 principios publicados por Jakob Nielsen en 1995, base para
evaluar la usabilidad de un producto digital. Son reglas GENERALES
("heurísticas"), no directrices estrictas.

Los 10 principios:
  1. Visibilidad del estado del sistema: dar feedback claro y a
     tiempo sobre lo que está pasando (ej. confirmar si un formulario
     se envió bien o marcar exactamente qué campo tiene error).
  2. Coincidencia entre el sistema y el mundo real: usar el lenguaje
     del usuario, no jerga técnica (evitar mostrar un error "404" sin
     contexto).
  3. Libertad y control del usuario: permitir deshacer/rehacer y
     salir de un estado no deseado sin pasos complicados.
  4. Consistencia y estándares: no reinventar convenciones ya
     establecidas (ej. "like" = pulgar arriba, favoritos = estrella).
  5. Prevención de errores: diseñar para que el error no ocurra, en
     vez de solo mostrar un buen mensaje después.
  6. Reconocimiento antes que recuerdo: minimizar lo que el usuario
     debe memorizar, haciendo visibles opciones y acciones.
  7. Flexibilidad y eficiencia de uso: dar atajos a usuarios
     experimentados para acciones frecuentes.
  8. Estética y diseño minimalista: no mostrar más información de la
     estrictamente necesaria en cada momento.
  9. Ayudar a reconocer, diagnosticar y corregir errores: mensajes en
     lenguaje claro, sin códigos, que digan qué pasó y cómo
     solucionarlo (evitar "usuario o contraseña incorrectos" sin más
     contexto).
  10. Ayuda y documentación: si hace falta, que sea fácil de
      encontrar y concisa.


6. UX vs UI (diapositiva 52)
---------------------------------
UX (User Experience): cómo se SIENTE y FUNCIONA la interacción.
¿Es fácil, útil y agradable usar el sistema?
UI (User Interface): cómo se VE el sistema. ¿Es clara y
visualmente consistente la interfaz?

Frase clave: "UX decide el camino, UI pinta el camino."


7. REGLAS DE NEGOCIO Y MATRIZ DE TRAZABILIDAD (diapositivas 58-61)
--------------------------------------------------------------------------
Al identificar relaciones entre requerimientos, revisar:
  - Ambigüedades: el requerimiento debe tener una sola interpretación.
  - Contradicciones: revisar si un requerimiento pone en duda otro
    (ej. "el botón debe ser morado" vs. "la ECI debe tener un sistema
    de diseño con colores definidos").

Matriz de trazabilidad: inventario de los requerimientos del sistema,
con ID, nombre, cliente responsable, prioridad, estado y equipo
responsable — permite hacerles seguimiento a lo largo del proyecto.


8. PROBLEMAS DE USABILIDAD COMUNES (diapositivas 62-64)
---------------------------------------------------------------
Usabilidad: facilidad con la que los usuarios navegan y logran su
objetivo en un sitio/app (navegabilidad + acceso rápido a la
información).

12 errores comunes mencionados: falta de coherencia/consistencia, no
tener diseño responsive, mala estructuración de contenidos, exceso de
clics, texto poco legible, mal manejo de enlaces internos, errores de
formularios (sin ejemplos, sin validación), falta de búsqueda interna,
URLs/nombres de página mal definidos, no permitir volver al home,
imágenes sin texto alternativo, carga lenta, contenido abrumador y
poco accesible.


9. MANUAL DE IDENTIDAD VISUAL (diapositivas 65-73)
--------------------------------------------------------
Qué es: documento con los estándares de comunicación verbal/visual de
una marca — cómo presentarla de forma uniforme en cualquier canal.

Qué debe incluir:
  - Introducción: elemento central y valores/filosofía de la marca.
  - Nombre y eslogan.
  - Público objetivo.
  - Paleta de colores.
  - Tipografía.
  - Imágenes utilizadas.
  - Elementos visuales del diseño (botones, iconos, guía de estilo).

Conceptos relacionados:
  - Benchmarking visual: estudiar competidores para entender qué
    estrategias/prácticas funcionan y adaptarlas.
  - Guía de estilo: documento con reglas visuales (colores,
    tipografía, tono) para mantener consistencia.
  - UX Writing: definir las palabras/oraciones más idóneas para que
    la interacción sea breve, amigable y clara.
